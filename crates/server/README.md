# Сетевой сервер Temporal Chess

Как в `capablanca-chess-plus-3d`: Actix Web + PostgreSQL, JSON по WebSocket,
сервер передаёт команды и хранит согласованный журнал. Движок в сервер не включён:
проверку и пересчёт выполняют только клиенты. Один процесс сервера
обслуживает комнаты; несколько процессов требуют отдельного общего канала рассылки.

## Запуск

Создайте PostgreSQL-базу и пользователя, задайте `DATABASE_URL` (пример в корневом
`.env.example`). База должна быть отдельной от Capablanca: названия таблиц совпадают.

```sh
cp .env.example .env
# Отредактируйте DATABASE_URL под свою базу.
cargo run -p temporal-chess-server --release
```

Миграции применяются автоматически. `BIND_ADDR` по умолчанию `127.0.0.1:8080`.
Маршруты: `GET /health`, WebSocket `GET /ws`. Внешний HTTPS/WSS обслуживает Caddy.
Сервер не хранит фигуры, доски или мировые линии, присланные клиентами.

## Правила синхронизации

- Создатель выбирает белых, чёрных или случайную сторону. Другой игрок занимает
  оставшееся место по коду комнаты. Комната доступна сразу после создания.
- Место закреплено токеном, в БД хранится только SHA-256. Переподключение заменяет
  прежнее соединение этой стороны; прежний клиент больше не может отправлять ходы.
- При подключении клиент передаёт SHA-256 ревизии движка. Он автоматически считается
  при сборке из исходников и манифеста движка; для native и WASM одинаков.
  Подключиться к занятой комнате с другой ревизией нельзя.
- Когда оба игрока отключены, первый авторизованный клиент может открыть комнату
  новой сборкой. Старая история сохраняется; неподтверждённое предложение и его
  голоса удаляются при смене ревизии движка. Второй клиент должен иметь ту же сборку.
- `play_command` содержит ревизию журнала и одну строку команды NOLAN-CHESS.
  Сервер не разбирает команды и не проверяет очередь, ходы, шахи или парадоксы.
  Он сохраняет предложение с уникальным ID и рассылает `command_proposed` обоим игрокам.
- Каждый клиент независимо проверяет очередь и применяет команду к копии позиции,
  затем автоматически отправляет `command_vote`. Два положительных голоса разных
  сторон атомарно добавляют команду в журнал и увеличивают ревизию. Только после
  `command_accepted` клиенты устанавливают рассчитанную позицию и показывают анимацию.
  Бесконечный парадокс остаётся допустимым действием с поражением сделавшего ход.
- Отказ любого клиента удаляет предложение, не меняя позицию и журнал; причина
  передаётся обоим игрокам. Повторные и устаревшие голоса не записывают ход повторно.
- Предложение и голоса хранятся в PostgreSQL и восстанавливаются при переподключении
  и перезапуске сервера. Одновременно возможно одно предложение; срок жизни — 5 минут.
- Ревизия увеличивается для всех подтверждённых команд, включая бесплатные
  протаскивания, продолжение расчёта и отказ от реакций. Ход сохраняется в журнале,
  даже если исчез из мировой линии при пересчёте.
- Полная история читается только при подключении или синхронизации. На обычном ходе
  сервер обрабатывает одну команду и два голоса, независимо от длины партии.
- Сохранение, рассылка, снимки и замена соединений упорядочены внутри каждой комнаты.
- Ограничения: 10000 команд на комнату, 192 ASCII-байта на команду, 16 КиБ на входящее
  сообщение, 20 сообщений/сек на соединение. Есть heartbeat и ограниченные очереди.

Пример первого сообщения:

```json
{"type":"create_game","protocol":3,"engine_revision":"<64 lowercase hex characters>","side":"random","causal_gaps":false}
```

Клиент сохраняет токен автоматически: браузер — `localStorage`, нативный клиент —
`$XDG_DATA_HOME/nolan-chess/sessions` (по умолчанию `~/.local/share/nolan-chess/sessions`).
На Unix файлы новых токенов создаются с правами 0600. Код комнаты можно передавать
сопернику; токен предназначен только владельцу места. Токены привязаны к адресу сервера.
После перезапуска клиента введите прежний код комнаты. Вторая вкладка того же браузерного
профиля с тем же кодом восстанавливает ваше место; для второго игрока нужен другой профиль.

Локальный режим, экспорт и инспекция сохранены. Импорт, новая позиция и отмена хода
не меняют сетевую комнату: они доступны после выхода в локальный режим.

Режим комнаты задаётся `causal_gaps` при создании (обычно `false`), хранится
в PostgreSQL и передаётся обоим клиентам в `game_ready`. Протокол — версия 3; клиент и сервер нужно обновить вместе.
Миграция 0003 добавляет ревизии движка и таблицу неподтверждённых предложений.
Миграция 0002 сохраняет старые комнаты с `causal_gaps=true`.

## Проверка согласования

Тест работает только с явно указанной отдельной тестовой базой (не с `DATABASE_URL`):

```sh
NOLAN_TEST_DATABASE_URL=postgres://user:password@localhost/nolan_test \
  cargo test -p temporal-chess-server two_client_consensus -- --ignored
cargo test -p temporal-chess-bevy multiplayer::tests
```

Он проверяет два независимых голоса, повторную отправку и гонку голосов,
отказ, восстановление предложения, смену сборки и истечение срока предложения.
